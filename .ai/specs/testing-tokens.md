# 토큰 테스트 스펙 (Token Testing Spec)

이 문서는 **생성된 디자인 토큰**의 테스트를 작성할 때 준수해야 할 검증 범위를 정의해요.
공통 원칙(실패할 수 있는 테스트, TDD, 레이어 경계)은 [testing.md](./testing.md)를 먼저 읽어주세요.

대표 파일은 `packages/ui/src/styles/tokens/colors.test.ts` 예요.

---

## 0. 무엇을 검증하나요 — 외형이 아니라 데이터 계약이에요

토큰 테스트는 **"Button이 어떤 색을 쓰는가"를 검증하지 않아요.** 그건 외형이고 Storybook의 몫이에요.

여기서 검증하는 건 **토큰 자체가 지켜야 할 데이터 불변식**이에요.

- 모든 토큰이 sRGB로 표현 가능한가
- 램프가 단조로운가 (단계가 커질수록 어두워지는가)
- 코어 계열이 같은 단계에서 같은 명도를 갖는가

이 불변식은 **사람 눈으로 확인할 수 없어요.** `blue[500]`이 색역을 살짝 벗어났는지, `red[700]`의 명도가 0.5pt 어긋났는지는 봐서는 모르고, 놓치면 잘못된 색이 조용히 배포돼요. 그래서 자동화 대상이에요.

---

## 1. 검증 범주 (6범주)

`describe` 블록은 **"무엇을 지키는가"** 기준으로 나눠요. 기술 분류(색공간 변환, 문자열 파싱)로 나누면 깨졌을 때 무엇을 잃었는지 읽히지 않아요.

| 범주 | 무엇을 지키나요 | 이걸 깨뜨리는 버그 |
|---|---|---|
| **① 변환 신뢰성** | 검증에 쓰는 색공간 변환이 정확한가 | 변환식 오타 — 나머지 5개가 전부 거짓 초록불이 돼요 |
| **② 표기 계약** | `oklch()` 문법 · 알파 소유 | 생성기가 숫자 포맷을 잘못 뱉거나 누가 손으로 hex를 적어 넣음 |
| **③ 표현 가능성** | 모든 색이 sRGB 안에 있는가 | 목표 채도를 올리거나 램프를 넓혀서 양 끝이 색역을 벗어남 |
| **④ 스케일 계약** | 단계 집합이 같은가 · 단조로운가 | 계열마다 단계가 달라져서 semantic 토큰을 바꿔 끼울 수 없게 됨 |
| **⑤ 계열 정렬** | 코어 계열의 명도가 일치하는가 · 선언한 램프를 따르는가 | 생성기가 계열에 엉뚱한 램프를 물림 |
| **⑥ 파생 일관성** | 알파 계열이 원본과 짝을 이루는가 | 채도 클램프가 기본 계열에만 적용되고 알파에 빠짐 |

**①이 가장 먼저 와야 해요.** 나머지 5개가 ①의 구현 위에 서 있어서, ①이 틀리면 전부 의미 없는 초록불이 돼요.

## 2. 검증 구현을 일부러 중복시켜요

토큰 테스트에는 컴포넌트 테스트에 없는 함정이 있어요. **검증에 쓰는 계산을 생성기에서 import 하면 안 돼요.**

같은 함수를 공유하면 변환식 자체가 틀렸을 때 생성기도 테스트도 똑같이 틀려서 **영원히 초록불**이에요. `testing.md` §3이 경고하는 "검증 대상과 구현을 공유하기"에 해당해요.

그래서 이렇게 나눠요.

1. **①이 테스트 쪽 구현을 외부에 공표된 기준값으로 검증해요.** (sRGB 원색의 OKLCH 좌표처럼 우리가 정하지 않은 값)
2. 나머지 범주가 그 검증된 구현으로 토큰을 검사해요.

두 구현 중 어느 쪽에 오타가 나도 빨간불이 떠요. **이 중복은 제거 대상이 아니라 설계예요.**

## 3. 검사 대상을 하드코딩하지 마세요

계열 목록 같은 검사 대상은 **SSOT에서 파생시켜요.** 손으로 적어두면 새 계열이 추가됐을 때 검사가 조용히 그 계열을 건너뛰어요.

```ts
// ❌ 새 코어 계열이 생겨도 보호받지 못해요
const CORE_FAMILIES = ["blue", "red", "grey"];

// ✅ spec 에서 뽑으면 새 계열도 자동으로 포함돼요
const coreFamilies = Object.entries(FAMILIES)
  .filter(([, family]) => family.ramp === "core")
  .map(([name]) => name);
```

대신 **파생으로 바꾸면 새로운 구멍이 생겨요.** 계열 하나를 코어에서 빼면 검사 범위가 조용히 줄어드는데도 초록불이 떠요. 그래서 **기준선을 잠그는 테스트를 함께 둬요.**

```ts
it("코어 계열 명도(L) 정렬 검사에 blue·red·grey 가 포함되는지 확인해요", () => {
  // 셋 중 하나를 코어에서 빼는 건 설계 변경이라 의식적인 결정이어야 해요.
  expect(coreFamilies).toEqual(expect.arrayContaining(["blue", "red", "grey"]));
});
```

## 4. 생성물 동기화는 테스트가 아니라 CI가 봐요

`colors.ts`를 손으로 고쳐도 **타입 검사도 테스트도 통과해요.** 값이 바뀌었을 뿐 계약은 여전히 지켜지니까요.

이건 테스트로 잡을 문제가 아니에요. `pnpm check:colors`가 생성 결과와 커밋된 내용을 비교하고, CI가 그걸 돌려요.
