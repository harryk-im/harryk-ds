# 디자인 토큰 스펙 (Design Tokens Spec)

이 문서는 `packages/ui/src/styles/tokens/` 의 디자인 토큰을 다룰 때 준수해야 할 표준을 정의해요.
**색상 토큰을 추가·수정하거나 어떤 단계를 쓸지 고를 때** 읽어주세요.

---

## 0. 단일 원천과 생성 파이프라인 (가장 먼저 읽어주세요)

색상 토큰은 **손으로 적지 않고 생성해요.** 사람이 편집하는 파일은 SSOT 하나뿐이에요.

```
colors.source.ts  ──[ pnpm build:colors ]──┬──▶  colors.ts     (컴포넌트가 import 하는 토큰)
   ↑ 사람이 편집하는 유일한 파일             └──▶  tokens.json   (Figma / Token Studio 포맷)
```

| 파일 | 역할 |
|------|------|
| `src/styles/tokens/colors.source.ts` | **SSOT.** 램프·계열·채도 규칙을 선언해요 |
| `scripts/build-colors.ts` | 생성기. 명도마다 sRGB 최대 채도를 이진 탐색으로 찾아요 |
| `src/styles/tokens/colors.ts` | **산출물.** 손으로 고치지 마세요 |
| `tokens.json` | **산출물.** `global.color` 자리만 교체돼요 |

```bash
pnpm build:colors    # 토큰을 다시 생성해요
pnpm check:colors    # 생성 결과가 커밋된 내용과 같은지 확인해요 (CI 가 돌려요)
```

> **`colors.ts` 를 직접 편집하지 마세요.** 다음 생성 때 사라지고, CI 의 `check:colors` 가 잡아요.
> 타입 검사는 손편집을 잡지 못해요. 타입이 맞는지와 생성물이 최신인지는 별개예요.

**생성기가 필요한 이유**는 하나예요. "이 명도에서 이 색조가 sRGB 로 표현할 수 있는 최대 채도"는 닫힌 해가 없어서 손으로 계산할 수 없어요.

---

## 1. 설계 원칙 — 명도를 고정하고 채도가 양보해요

| 축 | 규칙 |
|----|------|
| **명도 (L)** | **램프가 결정해요.** 계열이 달라도 같은 단계면 같은 명도예요 |
| **채도 (C)** | **목표값일 뿐이에요.** sRGB 를 벗어나는 자리에서는 자동으로 깎여요 |
| **색조 (H)** | **계열의 정체성이에요.** 램프 안에서 절대 변하지 않아요 |

양보하는 쪽이 채도인 이유가 있어요. **명도가 어긋나면 같은 단계끼리 시각적 무게가 달라져서 스케일 자체가 의미를 잃어요.** `blue[500]` 과 `grey[500]` 의 무게가 다르면 semantic 토큰을 계열 사이에서 바꿔 끼울 수 없어요. 채도가 조금 낮아지는 건 눈치채기 어렵지만, 명도가 어긋나는 건 바로 보여요.

채도 상한은 `min(목표 채도, maxChroma(L, H) × 0.92)` 예요. `0.92`(`CHROMA_SAFETY`)는 안전 마진이에요. sRGB 경계에 값을 딱 붙이면 반올림이나 브라우저 구현 차이 하나로 색조가 틀어져요.

---

## 2. 램프 — core 와 surface

램프는 명도 사다리예요. **숫자가 클수록 어두워요.** (900 = 가장 어두움, 100 = 가장 밝음)

### core — 뚜렷한 영역을 그려요

`blue` · `red` · `grey` 가 함께 써요. 텍스트·보더·솔리드 배경처럼 **눈에 또렷하게 잡히는 자리**예요.

L 25% 에서 81% 까지 **7pt 등간격**, 9단계예요. 같은 단계면 계열이 달라도 명도가 같아서, **흰 배경 기준 명암비의 계열 간 편차가 7% 안에 들어와요.**

### surface — 뒤로 물러나요

`lightGrey` 전용이에요. 배경·서피스처럼 **내용을 받쳐주는 자리**예요.

L 83% 에서 99% 까지 **2pt 등간격**, 9단계예요.

| 단계 | L | 흰 배경 대비 | 쓰는 자리 |
|------|---|---|---|
| `lightGrey[100]` | 99% | 1.03:1 | 페이지 배경 |
| `lightGrey[200]` | 97% | 1.09:1 | subtle 배경 |
| `lightGrey[300]` | 95% | 1.16:1 | hover 배경 |
| `lightGrey[500]` | 91% | 1.31:1 | 약한 divider |
| `lightGrey[700]` | 87% | 1.48:1 | 보통 보더 |
| `lightGrey[900]` | 83% | 1.69:1 | 강한 보더 |

간격이 core(7pt)보다 촘촘한 건 배경이 그렇게 쓰이기 때문이에요. `페이지 → 카드 → hover → pressed` 로 겹쳐 쌓을 때 필요한 명도 차이가 1~2pt 수준이라, core 처럼 성기게 두면 중간 단계가 비어요.

> **surface 가 core 와 정렬하지 않는 건 의도된 예외예요.** 배경 전용 계열이라 다른 축에 살아요.
> 테스트도 `lightGrey` 를 코어 정렬 검사에서 빼고, 대신 자기 램프를 지키는지 따로 확인해요.

### core 단계는 언제 쓰나요

지금은 **"같은 단계면 계열이 달라도 명도가 같다"는 원리**까지만 확정돼 있어요. 단계별 권장 용도는 접근성 감사를 마친 뒤 이후 작업에서 채워넣어요.

지금 알아둘 것은 하나예요. **흰 글씨를 얹는 배경에 300번대(L 67%)를 쓰면 대비가 3:1 근처에 머물러요.** 흰 배경 대비 3:1 인 색 위에 흰 글씨를 얹으면 결과도 3:1 이거든요. WCAG AA(4.5:1)가 필요한 자리라면 500번대(L 53%)가 필요해요.

## 3. 계열 (Families)

| 계열 | 색조 | 목표 채도 | 램프 |
|------|------|-----------|------|
| `blue` | 263.18 | 0.125 | core |
| `red` | 25 | 0.13 | core |
| `grey` | 263.18 | 0.01 | core |
| `lightGrey` | 263.18 | 0.01 | surface |

무채색 계열(`grey` · `lightGrey`)에도 브랜드 컬러와 같은 색조를 아주 옅게(0.01) 넣었어요. 전체 톤을 하나로 묶어주는 장치예요.

램프에 속하지 않는 단독 색상으로 `black`(L 14%) 과 `white`(L 100%) 가 있어요.

### 알파 변형

각 계열마다 `Alpha15` 짝이 자동으로 생겨요. 원본과 명도·채도·색조가 같고 투명도만 달라요.

```ts
COLORS.blueAlpha15[500]   // blue[500] 과 같은 색, 투명도 0.15
```

> **임의의 투명도가 필요하면 토큰을 늘리지 마세요.** `withOpacity` 를 쓰면 돼요.
> ```ts
> import { COLORS, withOpacity } from "../../styles";
> withOpacity(COLORS.blue[500], 0.4)
> ```

## 4. 새 색상 계열을 추가하는 방법

`colors.source.ts` 의 `FAMILIES` 에 **한 줄**만 더하고 생성하면 끝이에요.

```ts
export const FAMILIES = {
  blue: { hue: 263.18, chroma: 0.125, ramp: "core" },
  green: { hue: 145, chroma: 0.12, ramp: "core" },   // 👈 이 한 줄
  // ...
};
```

```bash
pnpm build:colors
```

기본 9단계와 알파 9단계, 그리고 `tokens.json` 항목까지 한 번에 만들어져요.
**테스트도 자동으로 따라와요.** 검사 대상을 `FAMILIES` 에서 뽑아 쓰기 때문에, `ramp: "core"` 로 선언하면 코어 정렬 검사가 새 계열을 바로 포함해요.

추가한 뒤 확인할 것은 두 가지예요.

1. `pnpm build:colors` 출력에서 **채도가 얼마나 깎였는지** 봐요. 목표 대비 70% 아래로 떨어지는 단계가 많으면 목표 채도를 낮추는 게 나아요.
2. `pnpm test:ui` 로 토큰 계약이 지켜지는지 확인해요.

### 단계를 늘리고 싶다면

core 의 7pt 간격을 밝은 쪽으로 이어가면 **88%, 95%** 가 나와요. 나중에 `50` · `25` 단계가 필요해지면 규칙을 바꾸지 않고 그 자리에 덧붙이면 돼요.

> **미사용 토큰도 지워지지 않아요.** primitive 팔레트는 완비돼 있어야 semantic 토큰을 자유롭게 조합할 수 있어요.

## 5. 컴포넌트에서 쓸 때

색상은 하드코딩하지 않고 `COLORS` 토큰을 써요.

```ts
// {name}.css.ts
import { COLORS } from "../../styles";

export const buttonColor = {
  primary: { color: COLORS.blue[500] },
  secondary: { color: COLORS.grey[500] },
} as const;
```

- 텍스트·보더·솔리드 배경 → `blue` · `red` · `grey` (core)
- 페이지·카드·hover 배경 → `lightGrey` (surface)

`colors.source.ts` 를 컴포넌트에서 import 하지 마세요. 공개 계약은 **토큰 값(`COLORS`)이지 생성 규칙이 아니에요.** 램프를 계속 다듬는 시기라 `RAMPS` 나 `CHROMA_SAFETY` 를 노출하면 램프 조정이 breaking change 가 돼요.
